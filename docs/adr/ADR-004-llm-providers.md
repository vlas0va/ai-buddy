# ADR-004. Провайдеры LLM: stub по умолчанию + любой OpenAI-совместимый API

Статус: принято · Владелец: A · Требования: R27, R44, R45, R46, R79, R80

## Контекст
Самый дорогой риск — эксперт без ключа не пройдёт основной сценарий и поставит 0. Организаторы могут подставить свой ключ.
Команда хочет показывать демо и на локальной модели (Ollama на ноутбуке), и на облачной.

## Решение
- `LLM_PROVIDER=stub` по умолчанию: детерминированный роутер намерений (guardrails + правила + обученный классификатор — логистическая регрессия),
  разбор русских дат, извлекающие ответы по базе знаний с шаблоном. Проходит все сценарии, используется в CI и e2e.
- `LLM_PROVIDER=openai_compat`: любой OpenAI-совместимый endpoint `/chat/completions` (облачный провайдер, vLLM, Ollama).
  Переменные `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_TIMEOUT_S`, `LLM_TEMPERATURE`.
- Оба провайдера идут через один и тот же слой инструментов и выдают одни и те же SSE-события.
- Сбой или таймаут LLM → событие `error{retryable:true}`; при `LLM_FALLBACK_TO_STUB=true` ответ достраивается stub-ом, и
  пользователь видит пометку, что ответ сформирован в упрощённом режиме.
- Опционально — эмбеддинги (`EMBEDDINGS_BASE_URL`, `EMBEDDINGS_MODEL`, например `bge-m3` в Ollama) для гибридного поиска.

## Последствия
- Демо проходит без сети; реальная модель включается одной переменной.
- Пишущие сценарии (S3, S4, согласования) детерминированы в обоих режимах (ADR-007), поэтому качество модели не влияет на безопасность.
