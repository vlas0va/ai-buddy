## Сценарии

### S1. Мой план адаптации
Цель: показать этапы, статусы задач и следующий шаг (R18–R20). Шаблон плана — пункты `checklist.yaml` с ролью и периодом.
1. Стажёр входит → таймлайн из пяти периодов чек-листа (1 неделя, 2 неделя, 1 месяц, 2 месяц, после 3 месяцев), текущий подсвечен.
2. Задачи периода — пункты чек-листа для роли стажёра (CL-03, CL-04, CL-05…); пункты с шагами раскрываются подзадачами.
   Статусы: не начато, в работе, ждёт согласования, готово, просрочено.
3. Блок «Следующий шаг»: одна ближайшая задача + кнопка действия (спросить buddy / оформить доступ / черновик сообщения).
4. Цели, задачи и ожидания вносит наставник или руководитель (CL-01 шаг 4, CL-06); видны стажёру и наставнику.
5. План наставника (`mentor.oleg`): свои пункты чек-листа (CL-01, CL-02, CL-06, CL-12, CL-13, CL-16) + прогресс стажёра,
   включая какие доступы и каналы стажёр уже запросил (CL-01 шаг 2). Отдельный интерфейс не нужен — вид по роли (R67).
6. Отметка «готово» — оптимистичное обновление < 1 с (R76).
7. Задачи, закрытые действиями S3/S4, получают ссылку на заявку.
8. ИИ-крон раз в сутки (в демо — кнопка «прогнать сейчас») создаёт напоминания по периодам чек-листа обеим ролям:
   просроченные пункты, защита данных в 1-й месяц (CL-08), подготовка к экватору (CL-10, CL-11, CL-13), опрос (CL-15, CL-16).
9. Пункты `human_only` (знакомство с командой, 1:1 с обратной связью, экватор, выпускной) buddy только напоминает — R05.

### S2. Спроси buddy
Цель: ответы о команде и инструментах с учётом контекста (R15), сокращение рутины наставника (R05).
1. Стажёр пишет вопрос. Статусы в потоке: «ищу в базе знаний» → «формулирую ответ».
2. Агент получает контекст: команда, роль, этап, открытые задачи плана.
3. Поиск по базе знаний только среди документов, доступных роли и команде (фильтр до LLM).
4. Ответ со ссылками на источники; на каждом — плашка «Тестовая инструкция прототипа» (R69).
5. Нет ответа или вопрос требует человека → «Это лучше уточнить у наставника» + черновик сообщения; стажёр отправляет.
6. Наставник отвечает в своём виде → ответ можно добавить в базу знаний команды (FAQ растёт, R10).
7. Запрос про чужие данные, зарплату, медицину, увольнения → вежливый отказ + к кому обратиться (R71–R72).
8. Оценка ответа: «Полезно / Не полезно» → событие для метрик.
9. Темы базы знаний, обязательные по чек-листу: кто есть кто и к кому идти (CL-03), документы и мануалы команды (CL-07),
   основы защиты данных — только тестовые версии и отсылка к официальным документам (CL-08), памятка о практике и учебных
   работах (CL-09), подготовка к экватору (CL-10, CL-11), методичка наставника — через куратора (CL-02).
10. Адресаты эскалации: наставник, руководитель, куратор стажировки (методичка, презентация экватора, выпускной), HR BP.
11. Опционально, если останется бюджет: «Конспект встреч» (CL-04 шаг 3) — приватные заметки стажёра, видимые только ему;
    buddy ищет и по ним. Заодно хорошая демонстрация прав: чужой конспект не находится.

### S3. Оформить отгул (основной сценарий для допуска)
Цель: действие через имитацию корпоративного сервиса (R17), определение «выполнено» (R66), пример из ТЗ (R04).
1. «Хочу взять отгул в пятницу» → buddy объясняет порядок из тестовой инструкции.
2. Уточняет даты и тип, проверяет (дата в будущем, не выходной, нет пересечений).
3. Показывает черновик заявки карточкой: даты, тип, согласующий (руководитель из справочника).
4. Стажёр нажимает «Отправить». Без подтверждения запись не выполняется.
5. Агент вызывает `absence.create_request` (MCP) от имени пользователя, с идемпотентным ключом.
6. Карточка результата: номер заявки, статус «На согласовании», согласующий.
7. Результат сохранён в `actions`, привязан к задаче плана; виден после перезагрузки.
8. `lead.maria` согласует → статус меняется на «Согласовано» у стажёра (событие → обновление).
9. Buddy напоминает: если отгул влияет на задачи, предупредить наставника — не заменяя общения.
10. Сбой сервиса → понятное сообщение, «Повторить», без дубля заявки (R79).

### S4. Доступы и каналы (основной, сразу после S3)
Опора в чек-листе: доступы и каналы упоминаются в первой неделе и у стажёра (CL-04, CL-05), и у наставника (CL-01).
1. «Какие доступы мне нужны?» → список для команды со статусами: Confluence, Jira, пространство кластера/команды и т. п.
2. Заявка на обычный доступ → `access.request_access` → статус и карточка результата, сохранение (R66).
3. Доступ с повышенными правами (например, закрытое пространство) → только через согласование руководителя (`approvals`).
4. Каналы и чаты: buddy показывает список каналов команды и готовит черновик просьбы наставнику добавить в них (CL-04 шаг 1).
5. Наставник в своём плане видит, что стажёр уже запросил, и отмечает CL-01 шаги 1–2.
6. Попытка запросить доступ от имени другого или к чужой системе → отказ, операция не выполняется (R71).
Если отстаём по графику: урезаем до шагов 1–3 и 6, каналы оставляем ответом без черновика — но S4 не выкидываем.

## Вне рамок
- Чувствительные ПДн и финансовые операции (зарплата, суммы компенсаций по бенефитам, медицинские сведения).
- Найм и увольнения — не задачи стажёра: только справка и перенаправление.
- Командировки и бенефиты — справочные ответы без операций.
- Отдельные интерфейсы наставника и руководителя — их действия в том же интерфейсе по роли.
- Своя HR-система, авторизация, ролевая модель — только имитации API.
- Замена 1:1, ревью компетенций, обратной связи, экватора и выпускного.

## Метрики пользы (R24)
| Метрика | Тип | Событие-источник |
|---|---|---|
| Время до первой самостоятельной задачи, дни | главная | `plan.task_done` для задачи «первая задача» |
| Рутинные обращения к наставнику на стажёра в неделю | эффект для наставника | `chat.escalated` |
| Доля вопросов без эскалации | качество | `chat.answered`, `chat.escalated` |
| Доля оценок «полезно» | качество | `chat.feedback` |
| Действия, успешные с первой попытки; время от намерения до заявки | снятие рутины | `action.created`, `action.failed` |
| Доля шагов чек-листа в срок | дисциплина адаптации | `plan.task_done`, `plan.task_overdue` |
| Использование после выпускного | точка входа | `session.started` для роли alumni |
| Ошибки на эталонном наборе, корректные отказы вне прав (цель 100%), p95 отклика UI | защитные | eval, тесты, Grafana |
Базовая линия для нагрузки наставника: 40–48 ч за 6 мес., 55–65 ч за 9 мес. (оценка Авито, R06).

## Как проверить эффект на стажёрах (R25)
1. Пилот на одной когорте: включение через runtime feature flag по командам (рандомизация по командам, а не людям — советы не перетекают внутри команды).
2. Контроль: команды без buddy в той же когорте + прошлая когорта; оценка difference-in-differences.
3. Опрос стажёров и наставников на 2-й неделе и на экваторе (короткая анкета + дневник времени наставника 2 недели).
4. Когорты малы → сначала метрики с большим числом событий (обращения, заявки), доверительные интервалы, решение о раскатке после экватора.
5. В прототипе: события пишутся в Kafka, дашборд Grafana на синтетике показывает все метрики таблицы.

## Сценарий видео (R42), 3–4 минуты
1. Вход стажёра → план (S1), следующий шаг.
2. Вопрос о процессе команды → ответ с источником и плашкой (S2).
3. Отгул: запрос → черновик → подтверждение → номер заявки → перезагрузка, заявка на месте (S3).
4. Вход руководителя → согласование → у стажёра статус обновился.
5. Попытка узнать отпуск коллеги → отказ (права).
6. Grafana: метрики; терминал: `make coverage` > 80%.
